#+TITLE: How auto-side-windows works
#+OPTIONS: toc:2

This document describes the implementation.  The [[file:../README.org][README]] tells you how
to use the package.

* The entry in display-buffer-alist

=auto-side-windows-mode= adds one entry to =display-buffer-alist=:

#+begin_src emacs-lisp
  (add-to-list 'display-buffer-alist
               '(t auto-side-windows--display-buffer) t)
#+end_src

The mode removes the entry when it goes off.  One entry is enough,
because the package asks its own rules for each buffer.

The entry goes at the end, which is what the last argument of
=add-to-list= says.  =display-buffer= takes the first entry that
matches and a =t= condition matches every buffer, so at the front this
one would shadow every rule the reader wrote.

The condition of the entry is =t=, so =display-buffer= offers each
buffer to =auto-side-windows--display-buffer=.  The function answers
with a window, or with nil.  A nil answer sends the buffer the way
that Emacs would take it without the package.

* How the package finds the side

=auto-side-windows--get-buffer-side= asks these questions, in this
order:

1. Does the action alist name a side?  =auto-side-windows--named-side=
   reads two keys.  =auto-side-windows-side= names a side that the
   buffer keeps: the commands that send a buffer to a side use it, and
   so can any caller.  =auto-side-windows--side= names a side for one
   display only: the slot swap and the way back from the toggle use it,
   so a side that the rules chose stays with the rules.  This question
   comes first, because =detached= is no side to hand on to a side
   window.

   The key is the package's own, and not =side=, because the entry
   above offers this package every buffer Emacs displays, and =side=
   in an action alist is each package's own word for a place on the
   frame: a side window to =display-buffer-in-side-window=, a
   direction to =display-buffer-in-direction=, a way to split to a
   package that splits for itself.
2. Is the buffer detached?  =auto-side-windows-toggle-side-window=
   sets =auto-side-windows--detached= in the buffer.  The buffer then
   goes to an ordinary window.
3. Does the buffer know its side?  =auto-side-windows-side= holds it.
   A file sets the variable as a file-local variable, and every
   display whose action alist names a side with that key sets it: the
   commands a reader sends a buffer to a side with, and callers such as
   an agent shell with a display action of its own.  The buffer then goes there
   again by any route, =switch-to-buffer= among them.  A side that the
   rules chose is not written: it is chosen again the next time, so a
   buffer follows a rule that changes.

   Both variables are permanent-local.  A buffer that sets up its
   major mode again for new content, as *Help* does for each
   description, keeps the side the reader gave it.
4. Do the rules of a side match?  The package tries top, bottom, left
   and right, in this order.

The rules of a side are the buffer names, the major modes and the extra
conditions of that side.  =auto-side-windows--side-condition= reads them
from the option table and puts them into one condition for
=buffer-match-p=: =(or NAME... (derived-mode . MODE)... EXTRA...)=.  Each
condition that =buffer-match-p= takes also works in the extra
conditions: a regular expression, a cons cell such as =(category
. comint)=, or a function.  A side nobody wrote a rule for makes =(or)=,
which matches nothing.

* The slot

A side of a frame holds a number of windows.  =window-sides-slots=
gives the number for each side, and a window has a slot number in its
side.

=auto-side-windows--get-next-free-slot= walks the slots of the side
from zero.  It returns the first free slot, or the slot of a window with
a buffer of the same major mode, if =auto-side-windows-reuse-mode-window=
names the side.

A side that holds as many windows as =window-sides-slots= allows is
full, whatever slots those windows sit in.  Emacs splits no window on a
full side: it reuses the window whose slot lies nearest the one it is
handed, and a free slot number can point at any window of the side.
The function therefore returns the highest slot at or above zero of the
windows that are there: the reuse is an exact match, the new buffer
replaces the buffer of the last slot, and a negative slot is left
alone.

A caller can name the slot instead, with a =slot= in the action alist.
=auto-side-windows--display-buffer= then takes that number and skips the
reuse of a window that shows the buffer already, because a caller who
names a slot means that slot.  That is how a buffer changes slot without
anyone setting the buffer of a window: see moving a buffer along a side.

The search counts up from zero and never returns a negative slot, so a
caller that asks for one keeps it.  =dirvish-side= displays itself in
slot -1, and the search gives that slot to no other buffer.  The reuse
of a window of the same major mode is the exception: it takes the
window whatever its slot.

* The display

=auto-side-windows--action-alist= puts three things together:

- the window parameters: the common ones, the ones of the side, and
  the ones the caller of =display-buffer= brought
- the action alist: the common one and the one of the side
- the side and the slot

Emacs reads the first entry of a name it finds and no other.  The side
and the slot therefore go first: they are the answer of this package,
and they carry the slot the caller asked for.  The parameters follow in
one =window-parameters= entry, in front of the alist of the caller,
and they are set in the order of the list, where the last of a name
wins: the common ones, the ones of the side, then the caller's, which
win.

=auto-side-windows--side-options= names every option of a side: its
window parameters, its action alist, its size, and the three rules that
send a buffer to it.  =auto-side-windows--side-option= reads one part of
one side from it.  The names are written out.  The compiler therefore
reads them, and a search finds them.

=auto-side-windows--display-buffer= then reuses the window that shows
the buffer already, or it calls =display-buffer-in-side-window= with
that alist.  A reused window can be an ordinary window, except where the
action alist names a side: the buffer is to go to that side then.  After
an ordinary window the buffer went to no side, so
=auto-side-windows-after-display-hook= does not run for it: the hook is
there to dress a side window, and an ordinary window is not one.
=auto-side-windows--claim= runs the hook for a side window, writes a
named side into the buffer and preserves the size.

The commands name =auto-side-windows--display-buffer= in their own
display action, so they work with the mode off as well.

* The geometry of a side

The size of a side window is given when the window is made, from the
action alist that =display-buffer-in-side-window= receives, and Emacs
keeps nothing afterwards.  Three parts of this package hold it, so that
a window which goes and comes back is made with the size the reader
gave it.

=auto-side-windows--geometry= and its setter keep an alist of
=(SIDE (size . SIZE) (slots . ((SLOT . SIZE) ...)))= in the current
tab.  A tab is where Emacs
keeps a window configuration, so the sizes of a layout belong to the tab
that shows it: each tab keeps its own, a new tab has none and starts from
the options, and a tab that closes takes its sizes with it.  No key is
needed and nothing has to be cleaned up, because the record is a key in
the alist of the tab itself.

There is a current tab whether or not =tab-bar-mode= is on: measured,
=tab-bar-tabs= answers =((current-tab (name . "*scratch*") ...))= in a
frame that never showed a tab bar, and it puts that list into the frame.
A frame without tabs therefore keeps its sizes in the tab it does not
show, and the package needs no second place to put them.

=auto-side-windows--measure= runs from
=window-size-change-functions=, which names the frame whose windows
changed.  That frame is the one measured, and not the selected one, so
that a side window resized on a second frame is written against the tab
of that frame.

It measures only a resize of the reader's.  After each command
=auto-side-windows--note-resize=, on =post-command-hook=, marks a resize
in =auto-side-windows--resized= when one of three things holds:

- The command is one of =auto-side-windows-resize-commands=.
- The event is a move of the mouse, and the commands since the last
  one of the list were moves too.  A drag of a divider begins with
  =mouse-drag-vertical-line= or =mouse-drag-mode-line=, and each move
  after it is a command of its own, an anonymous closure of the drag's
  transient map.  A drag that selects text begins with
  =mouse-drag-region= and marks nothing.
- The event is the mouse event that ends such a drag.  It can come
  before the redisplay that measures the last move, and it is a plain
  =mouse-1= where the mouse came back to the place it started.

The next measurement takes the mark off, and so does the next command
that is none of these.  A size change that a timer or a process makes after that is not the
reader's, though =last-command= still names the resize until the next
key.

Measured with a function on =window-size-change-functions=: a transient
menu that fits its window reports =magit-dispatch= and the key =?=, a
key bound to =enlarge-window-horizontally= reports that command, and a
drag reports a closure and =mouse-movement=.  A window that fits itself
and a window that goes and gives its lines to a sister are therefore
not measured.  The preserved sizes are renewed at every size change,
measured or not.

A marked measurement records only the sizes that changed since the last
redisplay, as =window-pixel-width-before-size-change= and its sibling
tell.  A wider right side makes a bottom window between the sides
narrower, and the height a caller fitted that window to stays out of
the record.  The slots of a side are recorded only where the side kept
its length, so only a divider between two of its slots counts.  A
taller bottom side makes the left slots shorter, and those heights are
the frame's.

A remembered size that the frame cannot hold any more gives as much as
fits, through =window-resizable=.

The sizes are pixels, and the entries that give them back are functions
that call =window-resize= pixelwise.  A window resized pixelwise, as it
is with =window-resize-pixelwise= set, has no whole number of lines when
its header line is made of images: measured, a top window of 152 pixels
counted 9 lines before a neighbour closed and 8 after, with the same
152 pixels, and a =window-height= of 9 lines gave it back a line too
tall.  On a text terminal a pixel is a character, so nothing changes
there.

The measurement also calls =window-preserve-size= on every side window,
for the width of a left or a right side and the height of a top or a
bottom one.  Emacs then treats the window as fixed in that direction
when it distributes space: a window that closes or a frame that changes
leaves the side alone and the editing area takes the difference.  This
matters with =window-combination-resize= set to =t=, where a window
that closes gives its space to every sibling, a side window among them.
A preserved size is bound to the buffer the window showed and to the
size it had, so =auto-side-windows--claim= preserves the window again
after each display, and the measurement preserves it again after each
size change.  =adjust-window-trailing-edge=, which is what a drag of a
divider calls, resizes a preserved window when it has to, so the
reader's hand still moves it.

=auto-side-windows--sizes= turns a record into the two entries of an
action alist: the size of the side, a width for a left or a right side
and a height for a top or a bottom one, and the size of the slot along
the side.  =auto-side-windows--action-alist= puts them behind the alist of
the caller, so Emacs applies them when it makes the window.

The order of that alist is the order of priority, because
=display-buffer-in-side-window= reads the first entry it finds: the
alist of the caller comes first, then what the reader last resized, then
the size option of the side, then the action alist of the side, then
the common action alist.  Nothing is taken out of the alist of a side:
a size left in it applies where the option is empty.

* Moving a buffer along a side

=auto-side-windows-move-to-next-slot= and its sibling take the buffer of
the side window at point to another slot of that side.  The slots that
exist are the only ones there are, so the buffer of the slot it moves to
comes back the other way and no slot is made or left empty.  The last
slot leads back to the first.

The swap deletes the two windows and displays both buffers again, each
with the slot of the other in its action alist.  Three things follow:

- Each buffer arrives through the display path, with the parameters and
  the action alist of its side and with the hooks run for it.
- Each window is a new one.  Emacs clears the buffer history of a window
  it makes, and a side window that offers the buffer of its neighbour to
  =switch-to-prev-buffer= shows two buffers where the reader put one.
- The sizes come from the side again: the slots get back the sizes
  that were measured when the reader resized them.  A side window a
  reader made taller stays the taller one, whichever buffer moves into
  it.

=auto-side-windows-drag-slot= does the same from the mouse.  Emacs binds
a press on a header line to =mouse-drag-header-line=, which resizes the
window and lets no =drag-mouse-1= out, so the command takes the press
and follows the mouse itself.  It asks whether the press began in a side
window before it follows anything: a press this command does not answer
belongs to whoever else wants it.

The package binds no key, this one included.  A keymap on the header
line of a side window takes the press before Emacs does; the README
shows it.

* The toggle

=auto-side-windows-toggle-side-window= moves the buffer of a side
window into an ordinary window, and back.

The command writes the side of the window into
=auto-side-windows--detached=, deletes the side window and displays
the buffer again.  The buffer then goes to an ordinary window, because
a detached buffer has no side.  The second call takes the mark off and
displays the buffer on the side the mark named: the buffer goes back
where it came from, whether or not a rule of the package names that
side, and whoever made that side window.

A buffer that is in no side window and carries no mark has none to
leave and none to go back to.  The command says so with a
=user-error=; =auto-side-windows-display-buffer-on-side= is the one
that sends such a buffer to a side.

Both directions go through =pop-to-buffer=, so the reader stays with
the buffer wherever it went, from a command and from Lisp alike: a
=post-command-select-window= waits for =post-command-hook=, which a
call from Lisp never reaches.

The command acts on the buffer of the selected window, which for a
command is the current buffer, and from Lisp need not be.
=auto-side-windows-display-buffer-on-side= leaves the selected window
alone unless it shows the buffer being sent.

* Known cost

=auto-side-windows--display-buffer= runs for each buffer that Emacs
displays, because the condition of its entry is =t=.  A buffer that
matches no rule costs 50 to 60 microseconds, measured over 20000 calls
in a batch session with rules on all four sides.  This is the price of
one entry that asks its own questions.

* The tests

=make test= runs the batch suite in
=test/auto-side-windows-test.el=.  It tests:

- the side of a buffer, for each of the four questions above, and that
  the side a reader gave a buffer outlives a new major mode
- the condition that the rules of a side make
- the free slot of an empty side, and the slot of a window that is
  there for a full side
- the options of each side
- that a buffer follows a rule the reader changes, that a command or a
  caller which names a side is remembered, and that a move or a toggle
  is not
- that a command sends a buffer to a side with the mode off, out of an
  ordinary window that shows it, and out of a window dedicated to it,
  and that the toggle takes a buffer back out of such a window
- the window parameters of a caller, over the ones of the side
- that an ordinary window that shows a buffer is reused without the
  after-display hook, and that a command called from Lisp leaves the
  windows of other buffers alone
- the toggle, in both directions, that the reader stays with the buffer,
  and where there is nothing to toggle
- the entry in =display-buffer-alist=, after the mode goes on and off
- the neighbour of a slot, and that the last leads back to the first
- the swap: which buffer is in which slot, that the windows are two and
  keep their sizes, and that neither offers the buffer of the other
- the drag, and that it does nothing across two sides, into an ordinary
  window, or where it began
- that the package binds no key
- the measurement: a resize command and a drag are marked, a marked
  measurement records only the sizes that changed, a window that fits
  itself and a window that goes are not measured, and the frame it is
  given is the frame it reads
- that the size along a side is preserved, holds when a window closes
  under =window-combination-resize=, and is preserved again after a
  resize; and that nothing is preserved where nothing is remembered
- that a side allowing no slot shows nothing and runs no hook
- which action alist entries a record turns into, for a side and a slot,
  and that the entry gives the window its pixels back
- that the switch forgets both the measuring and the giving back
- that the size of a side comes from its option before its alist

A batch session has a frame and windows, so the side windows and
their parameters are testable without a display.
